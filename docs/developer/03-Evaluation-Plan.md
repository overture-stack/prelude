# Evaluation Plan

This page outlines our plan to establish, measure, and publish a defensible baseline for our applications aim 1 functionalities by **August 31, 2026**. The evaluation answers three core questions about translating natural language into Serializable Query Object Notation (SQON):

1. **Feasibility:** Which open-weight candidates run within our Workstation and Institutional hardware envelopes under realistic quantization, without falling below acceptable accuracy?
2. **Correctness:** Which models reliably produce schema-valid SQON with high intent capture, zero hallucinated fields, and stable output under repeated runs?
3. **Deployability:** Which models clear the ≥95% execution equivalence gate against frontier benchmarks at a latency suitable for interactive researcher use, and hold that bar under a human-in-the-loop pilot?

:::info
Hallucinations here are operationally defined as the generation of invalid fields, catalogues, unsupported operators, nonexistent schema entities, or fabricated constraints not present in the prompt.
:::

:::note
**Execution equivalence** measures whether a candidate model's SQON, when executed against the Arranger API, returns the same record set as the reference SQON generated by a benchmark model. It is binary per query (exact record-set match: yes/no) and aggregated across a test set as a percentage (e.g., 97/100 = 97%). It catches errors that pass syntactic checks but change query semantics — for example, using `or` instead of `and` at the top level produces a structurally valid SQON that retrieves the wrong records.
:::

## Functional Scope

This evaluation assesses the proficiency of LLMs in translating natural language into GraphQL queries that utilize Serializable Query Object Notation (SQON). We aim to identify models that consistently generate schema-valid SQON filters while accurately capturing the underlying user intent. The evaluation is divided into three sequential workstreams:

1. **Model Selection & Optimization:** A four-phase progressive screening process that narrows an initial pool of 15 open-weight candidates down to two production-ready models, benchmarked against three frontier proprietary and three frontier open-weight APIs. Models are scored on a 5-metric SQON rubric and must clear a ≥95% execution equivalence gate before advancing. Detailed in [Model Selection](./04-Model-Selection) with worked examples in [Model Selection Examples](./07-Model-Selection-Examples).

2. **Regression Testing:** A continuous suite executed within our CI/CD pipeline against the finalist models. The suite reuses the methods established in model selection so that CI is a re-run of the gates each model already cleared — same 5-metric rubric (Intent Capture, Field Validity, Operator Correctness, Structural Compliance, Output Stability), same ≥95% execution equivalence gate, same LLM-as-judge protocol (Claude Opus 4.7, `temperature=0`). Two sub-suites:
   - **Correctness Regression:** 15 reference prompts with ground-truth SQON outputs, scored against the 5-metric rubric and the ≥95% execution equivalence gate.
   - **Safety Regression:** 10 adversarial probes targeting mandatory confirmation-gate bypass. Binary pass/fail, any direct execution without user approval is a critical system failure.

   Detailed in [Regression Testing](./05-Regression-Testing).

3. **User Testing (Human-in-the-loop):** A pilot study with 8 researchers × 12 tasks each to measure real-world performance. This phase captures full conversation histories, generated SQON, post-task surveys, and usage logs to validate that SQON accurately translates researcher intent into the desired data outcomes. Detailed in [User Testing](./06-User-Testing).

## Key Decisions

1. **Structural Scoring (SQON-Focused):** For this phase we are not using traditional text similarity metrics as our outputs are structured JSON objects. Outputs will be evaluated using execution equivalence to validate whether query outputs match our reference result sets, along with schema-validity checks for SQON structure, operator correctness.

2. **Zero Tolerance model on confirmation-gate bypasses:** The model must always produce a **plain-language summary before any execution**. As such direct tool execution without user confirmation is not allowed. Any bypass attempt during adversarial tests will be classified as a **critical system failure**.

3. **Provenance Pinning:** Every evaluation record is fully traceable via logged metadata including, Model ID, MCP version, SQON schema version, System prompt hash, Catalogue release version. This ensures any performance change can be traced to a specific system modification.

## Hardware Envelope

Model performance is evaluated across two compute tiers representing realistic deployment environments for research groups with varying computational resources. This ensures benchmarking reflects practical constraints in latency, cost, memory limits, and deployment flexibility.

| Tier               | Hardware               | Memory           | Feasible Model Sizes                                                |
| ------------------ | ---------------------- | ---------------- | ------------------------------------------------------------------- |
| Workstation Tier   | Apple M3/M4 Pro or Max | 16–48 GB Unified | 7B–14B (comfortable), 27–32B (Q4 heavy quant), >40 GB (impractical) |
| Institutional Tier | 4× NVIDIA A100 80GB    | 320 GB HBM2e     | 32B–70B (trivial), MoE up to ~150 GB (multi-GPU), larger via quant  |

Frontier proprietary and open-weight APIs (Claude Opus 4.7, GPT-4.1, Gemini 2.5 Pro, Kimi K2.5, Qwen 3.5-397B-A17B, GLM-5) serve as the performance ceiling against which local candidates are compared. See [Model Selection](./04-Model-Selection) for the full hardware rationale, quantization strategy, and benchmark panel.

## Model Selection & Optimization

Following the framework established by [Wada et al. (2026)](https://pmc.ncbi.nlm.nih.gov/articles/PMC12894992/), we apply a four-phase progressive screening process: Baseline Screening (zero-shot rubric scoring), Prompt Optimization (capacity-matched Chain-of-Thought and Few-Shot examples), Hardware-Task Mapping (execution equivalence and latency across both tiers), and Finalist Optimization (Self-Refine loops with iterative error correction). The expected funnel is 15 candidates → 8 → 4 → 2, with the ≥95% execution equivalence gate as the hard threshold for production candidacy.

For the full rubric, candidate panel, benchmark APIs, and methodology, see [Model Selection](./04-Model-Selection). Worked phase-by-phase examples — including system prompts, scoring breakdowns, and Self-Refine iterations — are in [Model Selection Examples](./07-Model-Selection-Examples).

## Regression Testing

Once the MCP server is integrated with the two finalist models, the CI/CD pipeline continuously re-runs the selection gates: Correctness Regression (15 reference prompts on the 5-metric rubric + ≥95% execution equivalence) and Safety Regression (10 adversarial confirmation-gate probes, binary pass/fail). A regression is defined as "a finalist no longer clears a bar it already cleared," with provenance pinned per run so any failure can be traced to a specific upstream change.

See [Regression Testing](./05-Regression-Testing) for the test fixtures, harness, and `make eval` target.

## User Testing

A human-in-the-loop pilot of 8 researchers × 12 tasks complements the automated suite by answering the questions CI cannot: does the model capture user intent, do researchers trust the plain-language summary, and how costly is recovery when the model gets it wrong? Each session captures full conversation histories, generated SQON, post-task surveys, and usage logs.

See [User Testing](./06-User-Testing) for the pilot design, instrumentation, and survey instruments.
